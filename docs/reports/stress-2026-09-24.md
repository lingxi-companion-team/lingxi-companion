# 压测与模糊标定报告

> 日期：2026-09-24 ｜ 主责：C（环境智能体 / 压测 / 集成）｜ 脚本：`tests/stress/`

## 0. 结论摘要

| 问题 | 结论 |
|:--|:--|
| 环境智能体单帧要多久？ | 中位 **1.96 ms**，其中**度量与合成 0.80 ms**、帧访问 1.16 ms（合成帧的口径，见 §1.3） |

## 1. 口径说明（先看这一节，否则数字会被误读）

### 1.1 为什么用合成帧

CI 只安装 `requirements-dev.txt`（**无 numpy / opencv**），压测必须与 CI 用同一套
依赖才能被自动化守住，因此帧一律由合成帧 `SyntheticFrame` 生成 —— 它定义在
`app/integration/sources.py`（同为 C 主责），由 `tests/stress/stresskit.py` 导入后
原样导出。定义只留一份：无摄像头时的全链路演示与压测载荷用的是**同一个**帧替身。

### 1.2 为什么合成帧是「按需计算」的

真帧的构造成本与分辨率成正比；若把构造计入测量，测到的是「造数据有多慢」。
`SyntheticFrame` 构造 O(1)，像素在 `frame[y][x]` 时才计算 —— 这与
`sample_luma` 的真实访问模式一致（只读 32×32 个块中心像素），所以能拿它压 1080p。

### 1.3 为什么单列一行「只采样」

合成帧的像素是**纯 Python** 算出来的（每次访问一次整数散列），而真帧是 numpy 数组、
单点访问快约两个数量级。若不做分解，绝对值会被载体成本主导，看起来像
「环境智能体要 2 ms」。因此报告的口径是：

```
评估耗时 1.96 ms  =  采样（载体成本）1.16 ms  +  度量与合成 0.80 ms
                                         ↑
                              这部分才是算法自身，且与载体无关
```

**可移植的数字是 0.80 ms**，不是 1.96 ms。分辨率结论（§3.1）不受此影响：
两种载荷的载体成本相同，比较的是同一口径下的差值。

### 1.4 三种纹理

| 纹理 | 表达的画面 | 主要分支 |
|:--|:--|:--|
| `noise` | 高频充足（清晰） | `E ≈ 1`，遮挡 0 |
| `flat` | 整帧同色（如镜头被挡） | `blur` 到顶 → `E ≈ 0`；遮挡平坦块判据 |
| `smooth` | 低频渐变（线性斜坡） | 拉普拉斯恒为 0 → 同样 `E ≈ 0` |

## 2. 复现方式

在仓库根目录执行（需要 5 项门禁所用的同一套依赖）：

```bash
python -m tests.stress.benchmark                    # 取本报告 §3.1–§3.3 的数字
python -m tests.stress.calibration                  # 取本报告 §3.4 的标定表
pytest tests/stress -q                              # 预算断言（CI 每次都会跑）
```

运行环境：Python 3.12.4、Windows AMD64、16 逻辑核。

## 3. 结果

### 3.1 环境智能体：分辨率与成本分解

| 载荷 | 中位 (ms) | p95 (ms) | 最快 (ms) | 次数 |
|:--|--:|--:|--:|--:|
| 320×240（噪声帧） | 1.8885 | 2.3948 | 1.8082 | 200 |
| 640×480（噪声帧） | 1.9715 | 2.7080 | 1.8632 | 200 |
| 1280×720（噪声帧） | 1.9032 | 2.5515 | 1.8221 | 200 |
| 1920×1080（噪声帧） | 1.9054 | 2.4556 | 1.8170 | 200 |
| 640×480（`flat` 帧） | 1.4487 | 2.0297 | 1.3921 | 200 |
| 640×480（`smooth` 帧） | 1.8774 | 2.6669 | 1.7852 | 200 |

**成本分解**：

| 载荷 | 中位 (ms) | 次数 | 说明 |
|:--|--:|--:|:--|
| 采样（1024 个块中心像素） | 1.1616 | 200 | 载体成本 |
| 评估一帧（采样 + 度量 + 合成） | 1.9625 | 200 | |
| 其中：度量与合成 | **0.8009** | — | 两者相减 |

**读法**：四个分辨率的中位值落在 1.89–1.97 ms 的窄带内（差别小于噪声水平），
说明耗时**只与采样点数有关、与帧像素数无关** —— 这正是「按采样点读取」这个
设计决策的直接后果，也是 `test_cost_is_independent_of_resolution` 守的性质。
`flat` 帧略快（1.45 ms）：像素函数走的是「返回常数」分支，省掉了散列计算。

### 3.2 融合层与串行链路

| 载荷 | 中位 (ms) | p95 (ms) | 最快 (ms) | 次数 |
|:--|--:|--:|--:|--:|
| 融合单帧（mock 共识场景） | 0.0162 | 0.0181 | 0.0152 | 600 |
| 串行链路单帧（环境真实 + 两路假 + 融合 + 平滑） | 2.0177 | 2.8844 | 1.9181 | 600 |

链路折算吞吐：**约 496 帧/秒**（采集侧只要求 15 帧/秒，余量约 33 倍）。

融合层本身（0.016 ms）与环境侧（1.96 ms）相比可忽略；链路只比环境单点多 0.06 ms，
差额就是融合与平滑的成本 —— 说明这两层目前都不是瓶颈。

### 3.3 长跑稳定性（3000 帧）

| 载荷 | 中位 (ms) | 尾/首窗口中位比 |
|:--|--:|--:|
| 串行链路 | 1.9884 | **0.98** |
| 环境智能体 | 1.9102 | **1.02** |

存活内存净增长：**1.5 KB / 3000 帧（约 0.51 字节/帧）**，即基本为零。

**读法**：单次成本若随调用次数增长（窗口忘截断、缓存越攒越大），比值会明显 > 1；
实测 0.98 与 1.02 是抖动范围。内存同理：每帧都会产出 `EnvContext` 与
32×32 网格（约 9 KB），若被累积，3000 帧就是 27 MB 量级 —— 实测 1.5 KB。

### 3.4 模糊标定（`_LAP_VAR_REF`）

方法：64×64 合成噪声作「高频充足」基准图 → **在图像域**连续施加 3×3 盒式模糊
（模拟失焦）→ 降采样到 32×32 → 记录拉普拉斯方差。

| 模糊遍数 | 拉普拉斯方差 | x = lap / 300 | blur | E（默认阈值） |
|--:|--:|--:|--:|--:|
| 0 | 100166 | 333.887 | 0.002 | 0.998 |
| 1 | 9109 | 30.362 | 0.021 | 0.973 |
| 2 | 1237 | 4.123 | 0.139 | 0.826 |
| 3 | 237 | 0.791 | 0.457 | 0.428 |
| 5 | 32 | 0.106 | 0.863 | 0.000 |
| 8 | 8 | 0.026 | 0.962 | 0.000 |

**两点结论**：

1. **容忍线（`blur_tolerance = 0.4`）落在「三遍盒式模糊」附近**（2 遍时 blur = 0.139，
   3 遍时 0.457，跨过 0.4）。也就是说系统在「肉眼已能看出糊、但尚未完全不可用」
   的位置开始明显降权，5 遍起 `E` 归零 —— 方向与单调性都对。
2. ⚠️ **原代码注释里的标定表不可复现，已按本表重写**。原表为
   `105508 / 1934 / 209 / 54 / 13 / 4`，并称「**两遍**盒式模糊落在容忍线附近」；
   实测同一方法得到 `100166 / 9109 / 1237 / 237 / 32 / 8`，首次越过容忍线在 **3 遍**。
   原表的 0 遍值与本次一致（说明基准图量级相同），但 1~2 遍值相差 5~6 倍，
   推测是**在采样网格上做模糊**（而非图像域）或用了不同的噪声源所致。
   **常数 300 本身未改** —— 改它会平移所有真实画面的 `E`，必须先定标再改。

⚠️ **方法学提醒（本次才发现）**：失焦必须在**图像域**做，因为它在光学上发生在降采样
之前。若先在 32×32 网格上模糊，等于在「已经丢掉高频」的信号上再丢一次，衰减会明显
偏慢（实测 1 遍：图像域降到约 2%，网格域只降到约 6%），据此标出的参考值会偏小。

## 4. CI 里守了什么

`tests/stress/` 的断言刻意只守**数量级退化**与**结构性性质**，不守绝对性能 ——
随机变红的压测等于没有压测（大家会习惯性重跑）。

| 断言 | 预算/阈值 | 实测 | 余量 |
|:--|--:|--:|:--|
| 环境评估单帧（4 个分辨率） | 20 ms | 1.9 ms | 约 10× |
| 融合单帧（4 个协商级别） | 5 ms | 0.016 ms | 约 300× |
| 串行链路单帧 | 20 ms | 2.02 ms | 约 10× |
| 串行链路 vs `pipeline.target_fps` | 66.7 ms（= 1000/15，**从配置推导**） | 2.02 ms | 约 33× |
| 1080p 耗时 ÷ 240p 耗时 | 5× | 约 1.0× | — |
| 长跑「尾/首窗口中位比」（1200 帧） | 3× | 0.98 / 1.02 | — |
| 长跑存活内存净增长（200 帧） | 128 KB（环境）/ 256 KB（链路） | 约 0.1 KB / 200 帧 | — |

**CI 时长**：`tests/stress` 全量约 **27 秒**；CI 里带 `--cov` 时约 **85 秒**
（覆盖率插桩让每条语句都多一次回调，整体慢约 3 倍 —— 这是测量开销，不是算法变慢）。

⚠️ 其中 `tracemalloc` 的内存类断言代价最高（tracing 给每次分配加约 15 倍固定
开销 —— 实测 200 帧要 5.7 秒、1000 帧要 29 秒）。因此帧数刻意压低到 200：
它只需做**粗筛**（是否按帧线性累积），调到 1000 帧只会让 CI 变慢而不会让结论更强。

⚠️ 改 `pipeline.target_fps` 会**自动收紧**端到端那条预算（这是刻意的：指标变了，
预算就该跟着变）。届时若真实模型接入后追不上，会先在压测里变红，
而不是等到演示时才发现卡顿。

## 5. 已知局限与待办

1. **不含真实模型推理**：本报告只覆盖「除模型外」的部分。200ms 端到端指标的
   验收必须等表情 / 行为两路交付后由 B 牵头重测。
2. **合成帧不等于真帧**：真帧是 numpy 数组，`sample_luma` 的访问成本会低约两个
   数量级；因此 §3.1 的绝对值偏悲观，而 §3.1 的**结论**（分辨率无关）不受影响。
3. **`_LAP_VAR_REF` 需在目标机上定标**：本表是在合成噪声上的量尺，不代表真实摄像头的
   绝对水平。换摄像头 / 光照后请重跑 `tests.stress.calibration`。锚点是否合理
   （「三遍糊」是否真的对应「还能用」）需与 A（全系统调参负责人）共同确认。
4. **压测尚未覆盖**：多线程 / 并发（`pipeline/` 尚未实现）、连续运行数小时的稳定性
   （当前上限 3000 帧）、内存峰值（只测了净增长）。
